## Context

| Concept | Description |
| --- | --- |
| Objective | Run and orchestrate containers. |
| Cluster | A group of virtual machines or physical servers, called nodes. |
| Node | A machine in the cluster where application containers run. |
| Desired state | A declarative configuration, often provided in a YAML file, that describes what should run. |
| Container runtime | Software on a node that runs containers, such as containerd or CRI-O. |
| Deployment | Describes the desired state for an application and manages its pods. |
| Pod | The Kubernetes object that runs one or more containers. |
| Service | Provides a stable way to connect to selected pods. |
| ConfigMap and Secret | Store configuration values; Secrets are intended for sensitive values. |
| Persistent volume | Provides storage that can outlive an individual pod. |

## How a deployment works

Developers use `kubectl`, the Kubernetes command-line tool, to send requests to the
control plane. Kubernetes then works to make the cluster match the desired state.

```text
Developer
    │
    ▼
kubectl (CLI; can submit YAML configuration)
    │
    ▼
Control plane
    │ schedules and manages application pods
    ▼
Worker nodes
    │
    ▼
Container runtime → Containers
```

The control plane is the brain of Kubernetes. It manages deployments and coordinates
which containers run on which worker nodes, so developers do not need to access nodes
directly to run containers.

## Control plane components

| Component | Role |
| --- | --- |
| API server | Receives requests to the Kubernetes API. |
| etcd | Stores the cluster's configuration and state as key-value data. |
| Scheduler | Chooses nodes for pods to run on. |
| Controller manager | Helps keep the cluster in the desired state, including by managing deployments. |
| Cloud controller manager | Provisions and manages resources from the cloud provider. |

## Worker node components

| Component | Role |
| --- | --- |
| Kubelet | Receives instructions from the control plane and makes sure containers are running on the node. |
| Container runtime | Runs containers on the node. Kubernetes uses containerd or CRI-O; Docker images can run here. |

## How users reach an application

An application may have multiple instances running in containers across nodes. A load
balancer distributes incoming requests to those instances. The cloud provider can
provision this resource for the cluster.

```text
Users
  │ requests
  ▼
Load balancer
  │ distributes traffic
  ▼
Application instances in containers
  │ run on
  ▼
Worker nodes in the cluster
```

| Cloud provider | Managed Kubernetes service |
| --- | --- |
| Azure | AKS |
| Google Cloud | GKE |
| Amazon Web Services | EKS |

Cloud providers can also offer managed resources, such as disks for persistent
application data, including database or file data.

## Kubernetes objects

Here is how Kubernetes objects fit together in an example where a web app
connects to a database.

### Deployments and pods

The web app runs in a container, and the database needs its own container.
Each can be described in a YAML file, such as `web-deploy.yaml` and
`db-deploy.yaml`. The files specify details such as the container image and
its registry.

Apply the files with `kubectl` to deploy them to the cluster:

```shell
kubectl apply -f web-deploy.yaml
kubectl apply -f db-deploy.yaml
```

Kubernetes runs containers in pods and manages the pods through Deployments.
Kubernetes works with pods rather than managing individual containers directly.

### Connecting the web app to the database

Each pod has an internal IP address, but using a database pod's IP address
directly in the web app's connection string is unreliable. If the pod restarts,
its IP address can change.

A Service provides a stable connection point and uses a selector to find pods
with matching labels. For example, a database Service can select the database
pod, and the web app can connect through that Service. A Service is described
in a YAML file, such as `db-service.yaml`.

```text
Web app Deployment → Web app pod
                           │
                           │ connection string
                           ▼
                     Database Service
                           │ selects matching pod
                           ▼
                     Database pod
                           │ mounts
                           ▼
                   Persistent volume
```

### Configuration and secrets

The database connection string contains sensitive data, so it should not be
stored as plain text in the web app's configuration.

- A ConfigMap stores non-sensitive configuration values.
- A Secret stores sensitive values. Secret data is base64-encoded in YAML
  manifests; this encoding is not encryption. Azure Key Vault or HashiCorp Vault
  can also be used to manage secrets.
- The web app pod can read a Secret value through an environment variable and
  use it as its database connection string.

### Persistent storage

Database files should not live only inside the database container. If the
container is lost, data stored only there can be lost too.

Instead, save the database files on a disk and attach storage to the database
pod using a PersistentVolume. The storage configuration includes capacity and a
storage class, which determines the type of storage provided (for example,
by Azure or AWS). Availability, backups, and service-level agreements depend
on the storage provider and its configuration.
